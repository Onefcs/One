## Общая оценка

Экономика уже сильно укреплена по сравнению с предыдущими аудитами
(`AUDIT.md`, `AUDIT-NET.md`): серверные гранты идут через единственную точку
`_commitServerItems`, действует инвариант переписи предметов (`_itemCensus`),
есть `invRev` против устаревших сохранений, потолок золота и XP-леджер,
cross-session-защита у маркета, кланового хранилища и большинства крафтов.

Оставшиеся дыры — **не архитектурные, а точечные пропуски в этих же
механизмах**: одна ветка забыла guard, который есть у соседних, одна проверка
переполнения не учитывает стакающиеся предметы, один хендлер удаляет предмет
без поля `slot`. Именно поэтому они и опасны: они попадают ровно в те сценарии
(реконнект на мобильном, полный инвентарь), для которых остальные защиты уже

# 1. Сохранения и загрузка

## Что уже сделано правильно (проверено, не баг)

Отвечая на вопросы прямо:

**Валидация перед загрузкой — есть.** `_sanitizeSavedStats`
(`server/index.js:2433`) пересобирает каждый предмет из канонического каталога
(`_canonSavedItem:2301` — от клиента берутся только `id`, `enhance`, `qty`),
отбрасывает неизвестные `id`, ограничивает длину массивов
(`_SANITIZE_MAX.invLen = 500`, `storageLen = 200`).

**Границы значений — есть.** `_clampInt`/`_clampNum` (`:2424`) отсекают
NaN/Infinity/отрицательные: `gold`, `lvl`, `xp`, `kills`, `bonusSP`, `maxHp`,
`hp`, `atk`, `def`. Отрицательного количества предметов быть не может:
`_canonSavedItem:2318` требует `qty >= 1` и клампит по `_SANITIZE_MAX.qty`.
`baseAtk/baseDef/baseMaxHp/xpNext` не берутся у клиента вовсе, а выводятся из
уровня (`:2484-2492`). `upgrades` сверяется с бюджетом `lvl*3 + bonusSP`
(`:2509`). Балансы, VIP, сезонные поля и `specialQuestsDone` из клиентского
блоба удаляются (`:2523-2555`).

**Защита от подделки — есть, но не контрольными суммами (S2).** Вместо
подписи используется инвариант: клиентское сохранение может только
**уменьшать** набор предметов (`_itemCensus:2388` + `_censusOverflow:2407`,
применяется на каждом `saveProgress:8898` и на `selectChar:7642`). Это строго
сильнее контрольной суммы, потому что checksum на клиенте всё равно
подделывается вместе с данными. Локальный бэкап сохранения из клиента убран
осознанно (`js/network.js:1530`) — там же написано почему. Плюс есть
`_looksLikeCatastrophicReset:2588` против затирания прогресса пустым блобом
и `invRev` против применения устаревшего сохранения поверх серверного гранта.

**Вывод:** отдельная контрольная сумма ничего бы не добавила; дыры не в этом
слое, а в перечисленных ниже конкретных хендлерах.

## S1. Часть полей сохранения не валидируется вообще

**Файл:** `server/index.js:2433-2557` (`_sanitizeSavedStats`), состав блоба —
`js/network.js:1497-1522` (`_buildSaveStats`).

`_sanitizeSavedStats` обрабатывает `inventory`, `storage`, `equipment`,
числовые поля и удаляет серверные. Но эти поля из блоба проходят **насквозь**
и пишутся в `savedData` как есть:

```
potionBag        (js/network.js:1505)   — количество HP-зелий
hudPotion, buffs                        — произвольный объект
skillLevels, passiveLevels              — passiveLevels клампится позже
advSkillLearned, advSkillActive         — не проверяется ничем
type                                    — класс персонажа
questIdx, questKills, floor
```

Последствия:

1. **`potionBag` — чистый фаусет.** Зелья покупаются целиком на клиенте
   (`js/npc.js:116` `buyPotion` — списывает золото локально и увеличивает
   `player.potionBag[...]`), сервер про них не знает ничего. Изменённый клиент
   пишет `potionBag: {pt1: 999999}` — сохранение принимается. Само по себе это
   меньшая проблема, чем **I3** ниже (там зелья вообще не нужны).
2. **`type` подменяем.** `gramShopBuy:5424` и `openLootBox:6326` берут класс из
   `_lastStats.type` — подменив его, можно купить/выбить оружие чужого класса.
3. **Произвольные ключи в `potionBag`/`buffs`** пишутся в документ игрока без
   ограничения размера (потолок — только `maxHttpBufferSize` 512 КБ на пакет).

**Воспроизведение:**
```js
// в консоли Mini App
player.potionBag = { pt1: 999999, junk: 'x'.repeat(100000) };
player.type = 'mage';           // при исходном классе lev
netSaveProgressNow();
// перезайти — обе подмены на месте, в БД тоже
```

**Рекомендация (не применялась):** прогонять `potionBag` через белый список id
`pt1`/`pt2` с клампом, валидировать `type` по `CHAR_DEF`, `skillLevels`/
`advSkill*` — по известным ключам, `buffs` — по известным ключам с клампом
длительности. Полноценно закрыть фаусет зелий можно только перенеся покупку
зелий на сервер (как уже сделано с `sellItem`).

# 2. Сетевая безопасность

## Что уже сделано правильно (проверено, не баг)

**Сервер — источник правды по всему, что стоит денег.** GRAM/Liberty живут
только в `_gramBalanceCache`/`_nexumBalanceCache` и двигаются атомарным `$inc`
(`_incBalance:387`, `_spendBalance:422`); из клиентского блоба они удаляются.
Все гранты предметов серверные. Урон, XP и золото за моба считает `Room.js`.
Позиция — намеренно клиентская (решение владельца, зафиксировано в
`Room.js:2271-2277`), HP — с лимитом реген-скорости `MAX_HP_REGEN_PER_SEC`
(`Room.js:2296-2315`).

**Валидация входящих пакетов — есть.** `safeOn:5163` ловит исключения и
throttle'ит логирование; `args[0] === null` нормализуется. Размер сообщения
ограничен (`maxHttpBufferSize: 512 * 1024`, `:1090`). Есть три бакета
рейт-лимита (`:4754-4765`): heavy 40/5с, amplifying 10/5с, fast 1500/5с, плюс
`_atkAllowed` 20 атак/с. Списки целей ограничены (`MAX_CC_TARGETS = 64`,
`Room.js:2930`), длительность CC клампится 6 секундами, множитель скилла — от 1
до 10 (`Room.js:2867`), есть серверный флор кулдауна скиллов `SKILL_CD_MS`
и проверка дистанции + line-of-sight (`Room.js:2861-2862`).
`spawnProj`/`spawnAoe` перебирают поля по одному через `_num`/`_color`
(`:8708-8732`). Неаутентифицированный сокет отваливается через 20 с (`:4466`).

**Античит по скорости/aimbot:** движение клиентское осознанно; aimbot по сути
неотличим от быстрого игрока, но урон и дальность считает сервер, так что
выигрыш ограничен `_atkAllowed`. Единственная реальная дыра в этом слое — I3.

## I3. `usePotion` — бессмертие: нет кулдауна, нет учёта зелий, обходит лимит регена (Критично)

**Файлы:** `server/index.js:7969-7973`, `server/game/Room.js:2322-2327`

```js
// server/index.js:7969
safeOn('usePotion', ({ amount } = {}) => {
  if (!currentRoom) return;
  const n = Number(amount);
  currentRoom.healPlayer(socket.id, Number.isFinite(n) ? Math.max(0, Math.min(n, 200)) : 60);
});
```

Хендлер проверяет только, что число конечное и ≤ 200. Он **не проверяет**:
- есть ли у игрока зелье (`potionBag` вообще не серверный — см. S1);
- прошёл ли кулдаун (`player.potCd = 4` секунды существует только на клиенте,
  `js/player.js:459-480`).

`healPlayer` (`Room.js:2322`) — это отдельный путь, который **намеренно
не проходит** через `syncPlayerHp` с его `MAX_HP_REGEN_PER_SEC = 30`
(комментарий на `Room.js:2307` прямо говорит: «Real heals … aren't gated by
this at all»). То есть весь смысл лимита регена обнуляется этим событием.

`usePotion` не входит ни в `_HEAVY_EVENTS`, ни в `_AMPLIFYING_EVENTS`, значит
попадает в fast-бакет: **1500 вызовов за 5 секунд = 300 хилов/с × 200 HP.**

Цена вопроса — реальные деньги: битва на смерть платит
`DEATH_BATTLE_GRAM_REWARD` в GRAM, арена 3х3 и Кровавая Башня — Liberty.

**Воспроизведение:**
1. Зайти в игру, записаться на битву на смерть (`deathBattleRegister`).
2. Во время боя выполнить в консоли:
   ```js
   setInterval(() => socket.emit('usePotion', { amount: 200 }), 20);
   ```
3. HP восстанавливается до максимума быстрее, чем любой противник успевает его
   снять. Персонаж неубиваем; награда за победу выплачивается на общих
   основаниях. `potionBag` при этом не тратится вообще.

**Рекомендация (не применялась):** серверный кулдаун на `usePotion`
(≥ 3–4 с, как `potCd` на клиенте), серверный учёт `potionBag` с
декрементом, и величина лечения из `ITEM_DEF[potionId].hp`, а не из пакета.

# 3. Игровая логика: сценарии, где предмет удаляется и не возвращается

## I1. Депозит в клановое хранилище при реконнекте удаляет ВЕСЬ стак осколков (Критично)

**Файлы:** `server/index.js:9650` (вызов), `:4966-5013` (`_applyGrant`),
`:158-183` (`_invFindOwned` / `_invRemove`), `shared/definitions.js:1132`
(`isStackableItem`).

Cross-session-ветка `clanStorageDeposit` перенаправляет списание осколков на
живой сокет:

```js
// server/index.js:9650
_target.data._applyGrant({ removeItems: [{ item: { id }, qty: n }] },
  'clan_storage_deposit_cross_session', { id, qty: n, clan: clan.name });
```

Передаётся объект `{ id }` — **без поля `slot`**. Дальше:

```js
// :4973  _applyGrant
(patch.removeItems || []).forEach(({ item, qty }) => {
  if (item) _invRemove(inv, qty != null ? { ...item, qty } : item);
});

// :170  _invRemove
if (isStackableItem(item)) {          // ← false: у {id, qty} нет .slot
  ...уменьшить qty на item.qty...
} else {
  inv.splice(idx, 1);                 // ← удаляется ВЕСЬ элемент массива
}
```

`isStackableItem(it)` определён как `it.slot === 'material' || ...`
(`shared/definitions.js:1132`). У `{ id, qty }` поля `slot` нет → функция
возвращает `false` → `_invRemove` идёт в ветку нестакающихся и **вырезает всю
запись инвентаря целиком**, независимо от `qty`.

Осколки — это `slot: 'material'` (`shared/definitions.js:1031`), они лежат
одним стаком, а уникальное легендарное оружие стоит 5000 осколков каждого вида
(комментарий на `:2225`). То есть игрок, копивший 5000 осколков, при депозите
10 штук в неудачный момент теряет все 5000.

Дополнительно: перед `_applyGrant` уже выполнен `$inc` клановому хранилищу
(`:9638-9645`), то есть в хранилище уходит `n`, а из инвентаря исчезает всё.
Разница уничтожается безвозвратно.

**Воспроизведение:**
1. Накопить стак осколков одного вида (например, 500 `shard_ruby`),
   состоять в клане ≥ `CLAN_STORAGE_MIN_DAYS` дней, хранилище открыто.
2. Отправить `clanStorageDeposit` с `{ id: 'shard_ruby', qty: 5 }`.
3. **В окне ожидания `await _myClan()`** (DB round-trip) переподключиться —
   на мобильном достаточно свернуть/развернуть приложение, либо
   искусственно: сразу после emit выполнить `socket.disconnect(); socket.connect();`
   и заново залогиниться, чтобы `activeSessions.get(tid) !== socket.id`.
4. Результат: в клановом хранилище +5 осколков, в инвентаре игрока запись
   `shard_ruby` исчезла целиком (было 500 → стало 0).
   В логах: `inv:clan_storage_deposit_cross_session` со `slots: N -> N-1`.

Проверить теорию без реконнекта можно юнит-вызовом:
`_invRemove([{id:'shard_ruby', slot:'material', qty:500}], {id:'shard_ruby', qty:5})`
→ массив становится пустым, вместо `qty: 495`.

**Заметка:** тот же `_applyGrant` в ветке `addItems` вызывается с полным
объектом из `CRAFT_MATS` (`:9843`), поэтому там всё корректно — ошибка ровно
в одном месте, где передан «голый» `{ id }`.

## I2. Проверка «инвентарь полон» игнорирует стакающиеся предметы → покупка и снятие с маркета уничтожают предмет (Критично)

**Файлы:** `server/index.js:7214` (marketCancel), `:7308` (marketBuy),
`:1885` (`_adminCancelListing`). Эталон правильной проверки —
`pickupWorldDrop:7078`.

Все три места проверяют место в инвентаре так:

```js
// :7308  marketBuy
if (_buyerInv && !isStackableItem(claimed.item) && _buyerInv.length >= SERVER_INV_MAX) {
  await _releaseClaim(listingId);
  return socket.emit('marketError', { msg: 'Инвентарь полон' });
}
```

Логика: «стакающийся предмет места не занимает». Но `_invAdd:187` даёт место
бесплатно **только если стак уже существует**:

```js
function _invAdd(inv, item) {
  if (isStackableItem(item)) {
    const existing = inv.find(i => i && i.id === item.id);
    if (existing) { existing.qty += item.qty; return true; }   // бесплатно
  }
  if (inv.length >= SERVER_INV_MAX) return false;              // ← сюда
  inv.push({ ...item });
  return true;
}
```

Если инвентарь на 150/150 и такого стака ещё **нет** — проверка пропускает
сделку, а `_invAdd` возвращает `false`. Дальше:

- **marketBuy** (`:7357`): GRAM уже списаны (`_spendBalance:7317`), лот уже
  `sold`, продавцу уже начислена выплата (`:7372`). `_delivered = false`,
  клиент получает `marketBought{delivered:false}` и **не добавляет предмет
  локально** (`js/ui.js:5102-5112` — «forging it here is exactly what the save
  path now rejects», показывается тост «предмет потерян»). Предмета нет нигде.
- **marketCancel** (`:7255`): лот уже переведён в `cancelled` (`:7217`),
  вернуть его нечем. Логируется `market_cancel_noroom`, предмет уничтожен.
- **`_adminCancelListing`** (`:1896`): то же самое, но по кнопке админа, и
  «Снять все лоты» (`/admin/market/cancel-all:1926`) прогоняет это по каждому
  активному лоту сразу.

Ровно эту ошибку уже чинили в `pickupWorldDrop` — там проверка правильная:

```js
// :7078
const _wouldStack = inv && isStackableItem(peek.item) && inv.some(i => i && i.id === peek.item.id);
if (inv && !_wouldStack && inv.length >= SERVER_INV_MAX) { ... }
```

В маркет и в админский путь это исправление не перенесли.

**Воспроизведение (marketBuy):**
1. Забить инвентарь покупателя ровно до 150 слотов, при этом **ни одного**
   `norm_stone` в инвентаре.
2. Второй аккаунт выставляет `norm_stone ×10` на маркет.
3. Покупатель жмёт «купить». GRAM списываются, лот становится `sold`,
   продавец получает выплату, покупатель видит тост «инвентарь полон, предмет

сохранении.

**Воспроизведение:** довести инвентарь до 150/150 и снять с маркета
несколько лотов, находясь в состоянии cross-session (реконнект в момент
снятия) без живого сокета. Инвентарь вырастает до 151, 152…; после этого
обычный `pickupWorldDrop` перестаёт работать навсегда.

# Что исправлено

Все 18 находок закрыты. Ниже — что именно сделано; номера строк относятся к
коду **после** правок.

### Общая часть: три новых примитива

Большинство находок оказались одной ошибкой в разных местах, поэтому сначала
появилась одна общая опора, а потом к ней подтянулись вызовы.

* **`_itemSlotOf` / `_isStackable`** (`server/index.js:165-172`) — слот предмета
  доопределяется по каталогу, если вызывающий его не передал. Это корень I1:
  `isStackableItem` смотрит только на `it.slot`, и объект `{ id, qty }` читался
  как нестакающийся, из-за чего **все** правила стаков инвертировались.
  `_invFindOwned`, `_invRemove` и `_invAdd` переведены на него.
* **`_invHasRoomFor(inv, item)`** (`:226`) — единственный ответ на вопрос «влезет
  ли», совпадающий с поведением `_invAdd`: стакающийся предмет проходит бесплатно
  **только если стак уже есть**. Заменил `!isStackableItem(item) && полон` во всех
  местах.
* **`_dbPushInventory(authed, items, reason)`** (`:2786`) — общий fallback-дозапис
  в БД, который никогда не отказывает (потерять оплаченный предмет хуже, чем
  переполнить инвентарь), но логирует `inv_over_cap`, когда аккаунт перевалил за
  лимит.

### Чего сознательно не делали

* **Покупка зелий осталась клиентской.** `potionBag` теперь валидируется и
  списывается сервером, но пополняется по-прежнему клиентом (за золото, у
  которого есть свой потолок роста). Полностью закрыть этот фаусет — значит
  перенести покупку зелий на сервер, как уже сделано с `sellItem`; это отдельная
  работа с изменением протокола, а не часть исправления потерь предметов.
* **`healParty` не трогали.** У него та же форма, что у `usePotion` (нет
  кулдауна), но лечить себя им нельзя, а серверный кулдаун на групповое лечение
  рискует задеть реальную механику хилера. Отмечено здесь как кандидат на
  отдельную задачу.
* **Движение осталось клиентским** — это зафиксированное решение владельца
  (`Room.js:2271-2277`), аудит его не пересматривал.
