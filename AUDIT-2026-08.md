## Критично

### C1. Бессмертие через `usePotion`

Весь контроль над лечением — на клиенте:

```js
// js/player.js:420
function usePotion() {
  if ((player.potCd || 0) > 0) return;      // кулдаун 4 с — только тут
  if ((bag[type] || 0) <= 0) return;        // наличие зелья — только тут
  bag[type]--;
  const heal = (def && def.hp) || 20;
  ...
  netUsePotion(heal);                        // сервер получает ЧИСЛО от клиента
}
```

Сервер:

```js
// server/index.js:7314
safeOn('usePotion', ({ amount } = {}) => {
  if (!currentRoom) return;
  const n = Number(amount);
  currentRoom.healPlayer(socket.id, Number.isFinite(n) ? Math.max(0, Math.min(n, 200)) : 60);
});
```

Не проверяется ничего: ни что зелье есть в `potionBag`, ни четырёхсекундный
кулдаун, ни сколько зелье вообще лечит. `usePotion` не входит в
`_HEAVY_EVENTS`, значит попадает в «быструю» корзину лимитера — **1500 событий
за 5 секунд, то есть 300 вызовов в секунду**.

300 × 200 HP = **60 000 HP восстановления в секунду**, бесплатно и вечно.
`healPlayer` выходит только при `hp <= 0`, а между двумя пакетами (3 мс) до нуля
не доводит ни один удар в игре. Практический результат — неубиваемый персонаж в
Битве на смерть (приз — GRAM и снаряжение), на Арене 3х3 и в Кровавой Башне
(приз — Liberty), в Войне гильдий и в обычном PvP.

Это ровно тот же класс дыры, что закрытая в `AUDIT.md` C2 — там починили `NaN`,
но не саму модель доверия: `amount` до сих пор приходит от клиента, а расход
зелья остаётся клиентским.

**Что делать.** Зелья уже лежат в `_lastStats.potionBag` на сервере (сохраняются
через `saveProgress`, `js/network.js:1509`). Значит handler может: взять тип
зелья из пакета (`pt1`/`pt2`), проверить остаток, вычесть его, взять `hp` из
`ITEM_DEF` по id, а не из пакета, и держать серверный кулдаун рядом с
`attacker._lastAtk` (там уже есть готовый образец, `Room.js:2751`). Плюс внести
`usePotion` в `_HEAVY_EVENTS`.

### C2. `healParty` — то же самое, но на всю группу

```js
// server/index.js:8051
safeOn('healParty', ({ amount } = {}) => {
  const healAmt = Math.max(0, Math.min(Math.floor(Number(amount)) || 0, 9999));
  ...
  if (currentRoom.healPartyMember(mid, healAmt)) io.to(mid).emit('healPartyMember', { amount: healAmt });
});
```

Ни кулдауна, ни проверки, что у кастера вообще есть этот скилл, ни проверки
класса. Тоже «быстрая» корзина: 300 вызовов в секунду × 9999 HP × 4 союзника.
Пати из пяти человек с одним модифицированным клиентом непобедима в любом
режиме. Проверка дистанции (`arePlayersNear`) есть и работает — она тут не
помогает.

**Что делать.** Серверный кулдаун на кастера (реальный кулдаун скилла — секунды),
верхняя граница по `computeStats(...).maxHp` цели вместо константы 9999, проверка
что класс кастера действительно владеет скиллом, и перенос в `_HEAVY_EVENTS`.

### C3. `partyAccept` не проверяет приглашение

```js
// server/index.js:8410
safeOn('partyAccept', ({ fromId }) => {
  if (!authed || playerParty.has(socket.id)) return;
  const fromSocket = io.sockets.sockets.get(fromId);
  if (!fromSocket) return;
  // ...дальше — вступление в пати
});
```

Нигде не хранится список отправленных приглашений. `partyInvite` просто шлёт
цели событие и ничего не записывает, а `partyAccept` принимает **любой**
`fromId`. socketId соседей клиент узнаёт из обычного потока мира
(`playerJoined`, `gameState`), так что цель всегда известна.

Последствия — реальные и не косметические:

* **Кража фарма.** `attack`/`skillAttack` делят XP и золото на всех членов пати
  в радиусе `PARTY_SHARE_R` (700 px, `Room.js:2931`): `xpShare = round(xp / totalMembers)`.
  Незваный сосед вдвое режет весь опыт и золото жертвы, и лут-винрейт с 100% до 50%.
* **PvP-иммунитет.** `_isPvpImmune` (`index.js:7680`) возвращает `true` для
  одной пати. Затащив жертву в пати, атакующий делает её неспособной ответить —
  и себя тоже, но это ровно тот инструмент, которым срывают дуэли и Войну гильдий.
* **Доступ к бафам.** `healParty` и `faithShield` (см. H6) начинают ходить между
  людьми, которые друг друга не выбирали.

**Что делать.** Хранить `pendingInvites: Map<targetSocketId, Set<fromSocketId>>`
с TTL порядка 15 с (клиент уже показывает таймер 15, `js/network.js:943`), и в
`partyAccept` требовать наличие записи, после чего удалять её.

## Высоко

### H1. `skillEffect` — стан любого моба на карте

```js
// server/index.js:7601
safeOn('skillEffect', ({ enemyId, enemyIds, type, duration } = {}) => {
  if (!currentRoom) return;
  if (enemyId) currentRoom.applySkillEffect(enemyId, type, duration);
  if (enemyIds) currentRoom.applySkillEffectMany(enemyIds, type, duration);
  ...
});
```

`applySkillEffect` (`Room.js:2893`) проверяет только что моб жив, и клампит
длительность до 6 с. **Нет проверки дистанции, нет проверки что моб вообще
виден игроку (`_raceVisible`), нет кулдауна, нет привязки к классу.**

`MAX_CC_TARGETS = 64` ограничивает один пакет, но не частоту: событие в «быстрой»
корзине, 300 пакетов/с × 64 цели = до 19 200 наложений стана в секунду с одного
сокета. Держать в перманентном стане можно что угодно по id: мирового босса,
босса Кровавой Башни, замок Войны гильдий, чужие волны в Страхе. Идентификаторы
мобов открыто ходят в `gameState` и в `enemySnapshot`.

Отдельно: обратная рассылка `enemyCC` отправляет клиентам **неклампленный**
`duration` — сервер держит 6 с, а у всех вокруг моб визуально «заморожен»
навсегда (`js/network.js:756`).

**Что делать.** Проверять дистанцию кастера до цели (как `skillAttackEnemy`:
600 px + LOS), проверять `_raceVisible`, ввести серверный кулдаун по образцу
`SKILL_CD_MS`/`SKILL_BURST_MS`, и рассылать уже склампленное значение.

### H2. `pvpSkillCC` — стан-лок игрока с любой дистанции

```js
// server/index.js:7718
safeOn('pvpSkillCC', ({ targetId, type, duration } = {}) => {
  ...
  const dur = Math.max(0, Math.min(duration, 6));
  _emitNearby(target.x, target.y, 'pvpPlayerCC', { targetId, type, duration: dur }, true);
});
```

Проверяются `pvpMode`, живость обеих сторон, безопасная зона и иммунитет
пати/клана. **Не проверяется расстояние** — в отличие от `pvpAttack` (500 px) и
`pvpSkillAttack` (600 px). И нет никакого кулдауна: событие в «быстрой» корзине.

Итог: любой игрок в PvP-режиме может быть застанен с другого конца карты, и
300 пакетов в секунду по 6 с каждый — это перманентная блокировка управления.
На Арене 3х3 и в Битве на смерть это прямая победа без единого удара.

Побочно: `Math.min(undefined, 6)` даёт `NaN`, и `player.stunTimer` на клиенте
навсегда становится `NaN` (`js/network.js:771`). Само по себе безвредно
(`NaN > 0` — false), но любой будущий `Math.max(stunTimer, x)` уже никогда не
вернёт число.

### H3. `privMsgHistory` / `privMsg` — сканы коллекции по запросу

```js
// server/index.js:2807
async function _resolveUsername(name) {
  return PlayerModel.findOne({ username: new RegExp('^' + _escapeRegex(target) + '$', 'i') }, ...);
}
```

`PlayerSchema` (`server/models/Player.js`) имеет индексы **только** на
`telegramId` (unique) и `bm`. Индекса на `username` нет, и даже был бы — якорный
case-insensitive regex его не использует. Каждый вызов — полный скан коллекции
Player.

Кто может его вызвать и как часто:

* `privMsgHistory` (`index.js:8146`) — **вообще без rate-limit**, не входит в
  `_HEAVY_EVENTS`, значит 300 вызовов в секунду с одного сокета.
* `privMsg` (`index.js:8129`) — формально ограничен `_lastChatAt` в 3 с, но
  `_lastChatAt = now` присваивается **после** `await _resolveUsername(...)`:

  ```js
  if (now - _lastChatAt < 3000) return;
  const msg = text.trim().slice(0, 100);
  if (!msg) return;
  const target = await _resolveUsername(toUsername);   // ← скан
  ...
  _lastChatAt = now;                                   // ← слишком поздно
  ```

  Пачка из 300 `privMsg` в одном тике проходит проверку целиком и запускает
  300 сканов.

При десятках тысяч аккаунтов это самый дешёвый способ положить базу: несколько
байт запроса против полного обхода коллекции, всё через тот же пул из 10
соединений, которым пользуются сохранения прогресса всех остальных.

**Что делать.** Добавить `PlayerSchema.index({ username: 1 })`, хранить
нормализованный (lowercase) username отдельным полем и искать точным
равенством вместо regex, внести `privMsg`/`privMsgHistory` в `_HEAVY_EVENTS`,
и поднимать `_lastChatAt` до `await` (см. M6).

### H4. Утечка памяти клиента: спрайты чанков карты

```js
// js/pixi-world.js:289
let spr = _chunkSprCache.get(key);
if (!spr) {
  let cv = _tileChunks.get(key);
  if (!cv) {
    cv = _buildChunk(cx, cy);
    if (_tileChunks.size >= _CHUNK_MAX) _tileChunks.delete(_tileChunks.keys().next().value);
    _tileChunks.set(key, cv);
  }
  const tex = PIXI.Texture.from(cv);
  spr = new PIXI.Sprite(tex);
  _tileCt.addChild(spr);
  _chunkSprCache.set(key, spr);      // ← никогда не удаляется до смены карты
}
```

`_tileChunks` — LRU на 96 канвасов, и комментарий рядом обещает «oldest evicted»
(`js/game.js:1640`). Но:

1. `_chunkSprCache` **не ограничен ничем**. Он очищается только в
   `pixiInvalidateChunks()`, который вызывается из `buildTileCanvas()` — то есть
   раз за подключение к миру, а не по ходу игры.
2. Вытеснение из `_tileChunks` **ничего не освобождает**: `PIXI.Texture.from(cv)`
   держит ссылку на тот же самый canvas через `BaseTexture`. Канвас остаётся
   живым ровно столько, сколько живёт спрайт.

Масштаб: мир — 254×1939 тайлов = 10160×77560 px = **7776 чанков**. Коридор в
высоту — 243 чанка. Чанк — 324×324 RGBA: ~420 КБ канваса + ~420 КБ GPU-текстуры.
Пробежка по одному коридору с забегом до босса — это сотни новых чанков; за
сессию легко набирается 300–500 → **250–400 МБ**, из них половина в VRAM.
На мобильном WebView внутри Telegram это заканчивается вылетом или тем, что
браузер начинает выгружать и переподгружать текстуры на каждом кадре.

Плюс постоянная стоимость: `_chunkSprCache.forEach(spr => { spr.visible = ... })`
выполняется **каждый кадр** по всей истории посещённых чанков
(`js/pixi-world.js:315`), и `_tileCt.children` растёт вместе с ней.

Это лучший кандидат на объяснение жалоб «чем дольше играю, тем сильнее тупит».

**Что делать.** Ограничить `_chunkSprCache` тем же LRU, что и `_tileChunks`
(и вытеснять их согласованно), при вытеснении делать
`_tileCt.removeChild(spr); spr.destroy({ texture: true, baseTexture: true })` —
код для этого уже написан в `pixiInvalidateChunks` (`js/pixi-world.js:141`).
Разумный запас — чанки в радиусе 2–3 экранов, порядка 60–90 штук.

### H5. `seasonRating` — полный скан на каждое открытие панели

```js
// server/index.js:6337
const rows = await PlayerModel.find({ 'savedData.seasonPoints': { $gt: 0 } }, ...)
  .sort({ 'savedData.seasonPoints': -1 }).limit(50).lean();
...
myPlace = await PlayerModel.countDocuments({ 'savedData.seasonPoints': { $gt: mine } }) + 1;
```

Индекса на `savedData.seasonPoints` нет. Значит: полный скан коллекции + сортировка
в памяти (а Mongo при in-memory sort свыше 32 МБ просто отдаёт ошибку — то есть
на достаточно большой базе рейтинг сезона перестанет открываться вовсе), затем
**второй** полный скан на `countDocuments`. Событие входит в `_HEAVY_EVENTS`,
но это всё равно 40 запросов за 5 секунд на сокет.

Сезон — это то, за что раздают реальные призы, так что панель открывают часто.

**Что делать.** `PlayerSchema.index({ 'savedData.seasonPoints': -1 })`.
Заодно: `/admin/stats` сортирует по `savedData.lvl`, `savedData.gold`,
`savedData.nexumBalance` и считает `countDocuments({ createdAt: { $gte } })` —
тоже без индексов (менее критично, эндпоинт админский и ограничен 240 запросами
в минуту, но при большой базе каждый вход в админку — четыре полных скана).

### H6. `faithShield` раздаёт бессрочный щит

```js
// server/index.js:7641
safeOn('faithShield', ({ duration } = {}) => {
  ...
  io.to(mid).emit('faithShieldBuff', { duration });   // как пришло, так и ушло
});
```

```js
// js/network.js:725
socket.on('faithShieldBuff', ({ duration }) => {
  faithShieldTimer = duration;      // без клампа
  recompute();
});
```

```js
// js/player.js:274
if (faithShieldTimer > 0) defMult *= 1.50;
```

`duration` — произвольное число от клиента. `faithShieldTimer = 1e9` даёт
союзникам +50% DEF на всю сессию. Серверный потолок это пропускает:
`DEF_BUFF_HEADROOM = 2.85` (`Room.js:114`) как раз рассчитан на стек
guard×faithShield, так что `statsUpdate` примет завышенный DEF без возражений.

Кулдауна тоже нет — событие в «быстрой» корзине.

**Что делать.** Клампить `duration` серверно (реальное значение —
`4 + _skillBuffSec('E')`, максимум порядка 10 с), плюс кулдаун на кастера.

## Средне

### M1. Публично раздаётся весь репозиторий

```js
// server/index.js:2132
app.use(express.static(path.join(__dirname, '..')));
```

`__dirname` — это `server/`, значит корень раздачи — корень проекта. Наружу
доступны `/server/index.js`, `/server/game/Room.js`, `/server/models/*`,
`/package.json`, `/package-lock.json`, `/AUDIT.md`, `/AUDIT-PERF.md`,
`/AUDIT-NET.md`, `/dev/*`.

Секретов в файлах нет (всё через `process.env`, а `.env` не отдаётся — у
`serve-static` `dotfiles: 'ignore'` по умолчанию), и клиентский код и так
собирается в `/bundle.js`. Но публичный исходник сервера — это готовая карта
всех античит-порогов: `GOLD_MAX_EARN_PER_SEC`, `XP_JOIN_SLACK_KILLS`,
`_SANITIZE_MAX`, `SKILL_CD_MS`, содержимое `_HEAVY_EVENTS` и точный список
того, что не проверяется (C1–C3, H1, H2, H6 выше). Плюс сами AUDIT-файлы — это
список известных слабых мест с адресами строк.

**Что делать.** Раздавать явный whitelist (`index.html`, `guide.html`,
`admin.html`, `css/`) вместо корня, либо перенести статику в отдельный
`public/`.

### M2. Спецквесты рендерятся без экранирования

```js
${q.desc ? `<div class="quest-desc">${q.desc}</div>` : ''}
<a href="${q.url}" ... onclick="_specialQuestPending.add('${q._id}');...">
```

`_questFields` (`server/index.js:1986`) только обрезает строки по длине —
`String(b.title).slice(0, 120)` — и не фильтрует ничего. Все четыре поля
попадают в `innerHTML` как есть; `q.url` попадает ещё и в атрибут `href`
(значит `javascript:` тоже проходит) и внутрь строкового `onclick`.

Источник — админ-панель, то есть это не «любой игрок». Но эффект — stored XSS
против **всех** игроков сразу (`/api/special-quests` отдаётся публично), а токен
админки живёт 7 дней и лежит в localStorage. Единственная сейчас цепочка от
компрометации админки к компрометации аккаунтов игроков.

**Что делать.** Экранировать при рендере (`_escHtml` уже есть в `js/ui.js`),
и на сервере пропускать в `url` только `https://`-схему.

### M3. `viewersOfEnemy` — O(всех игроков) на каждый удар

```js
// server/game/Room.js:1804
viewersOfEnemy(enemyId, exceptSocketId) {
  const out = this._viewerBuf;
  out.length = 0;
  this.players.forEach(p => {          // ← все игроки в мире
    if (!p._eKnown.has(enemyId)) return;
    out.push(p.socketId);
  });
  return out;
}
```

Вызывается из `_enemyViewers` на **каждый** `enemyHurt` и `enemyKilled`, то есть
на каждый удар по мобу в игре. `_atkAllowed` разрешает 20 ударов в секунду на
игрока. При 300 онлайн, из которых половина бьёт в темпе ~10 ударов/с:
1500 ударов/с × 300 обходов = **450 000 итераций Map в секунду**, внутри того же
потока, где крутится 25-мс тик.

Это последний оставшийся O(N)-по-игрокам путь в горячем бою — `AUDIT-PERF.md`
отмечал его как P2-3, но фактически он не изменился: перевод рассылки на
`_eKnown` убрал лишние **пакеты**, а не обход.

**Что делать.** Обратный индекс `enemyId -> Set<socketId>`, поддерживаемый там
же, где живёт `_eKnown` (`_pushEnemyEntry` добавляет, свип в `_collectEnemiesFor`
и `_forgetEnemy` удаляют). Тогда рассылка становится O(зрителей), а зрителей у
одного моба — единицы.

### M4. Каждый дроп: запись в базу + строка лога + весь инвентарь в сокет

`socket.data._grantKillLoot` (`index.js:4810`) на любой удачный ролл зовёт
`_commitServerItems` (`index.js:4757`), а тот делает три вещи:

1. `logPlayer(...)` → `PlayerLogModel.create(...)`, плюс каждые 25 записей два
   `find().sort({at:-1}).skip(N)` и `deleteMany`;
2. `_persistSavedFields(...)` → `findByIdAndUpdate` со всем массивом инвентаря;
3. `socket.emit('inventorySync', { inventory, equipment, invRev })` — **весь**
   инвентарь целиком, до 150 предметов JSON.

Частота по реальным константам: шанс предмета ~1.9% на 40+ уровне
(`itemDropChanceAtLevel`), ключи ~1.0%, камни ~0.012%, рецепты ~0.17% — итого
около **3% килов**. Для одного игрока это редко; для 300 фармящих игроков —
порядка 9 записей в Mongo и 9 вставок в PlayerLog в секунду плюс регулярные
trim-запросы, всё через тот же пул из 10 соединений.

Дороже другое: `inventorySync` с полным инвентарём (~20–30 КБ JSON у
прокачанного персонажа) улетает игроку **на каждый дроп**. За час фарма это
десятки мегабайт мобильного трафика на ровном месте — при том, что
`AUDIT-NET.md` считал час игры за 53 МБ суммарно.

У `PlayerLog` вдобавок нет композитного индекса: есть отдельно `telegramId` и
отдельно `at`, а trim-запрос фильтрует по первому и сортирует по второму.

**Что делать.** Слать дельту (`inventoryPatch` с изменёнными слотами) вместо
всего массива, коалесцировать запись и лог по образцу `_flushBalances`
(`BALANCE_PERSIST_MS`), добавить `PlayerLogSchema.index({ telegramId: 1, at: -1 })`.

### M5. Награда Кровавой Башни может исчезнуть

```js
// server/index.js:4050
for (const sid of participants) {
  const won = !!winnerId && sid === winnerId;
  const s = io.sockets.sockets.get(sid);
  let reward = 0;
  if (won && s?.data?._race10GrantWin) reward = await s.data._race10GrantWin();
```

`_race10.dmg` намеренно переживает выбывание («Their damage tally survives them»,
`index.js:4021`), и победителем становится тот, кто нанёс больше урона, —
независимо от того, жив он и подключён ли. Но выдача идёт через **сокет**:
если лидер по урону отключился (а разрыв связи на мобильном за 15-минутный забег
— обычное дело), `io.sockets.sockets.get(sid)` возвращает `undefined`,
`_race10GrantWin` не вызывается, и Liberty не получает **никто** — ни он, ни
второй по урону. В логе останется `race10_end` с `reward: 0`.

Тот же паттерн у `_dbGrantWin` и `_a3GrantWin`, но там победитель по определению
жив (последний выживший), так что проблема именно в race10.

**Что делать.** Выдавать через `_incBalance(telegramId, 'nexumBalance', ...)` по
`telegramId` (он известен из `_socketTid`, зафиксированного при деплое), а не
через живой сокет; сокет использовать только для уведомления.

### M6. Антифлуд чата обходится пачкой в одном тике

`chat` (`index.js:8071`) ставит `_lastChatAt = now` сразу — правильно.
А `clanChat` (`8084`) и `privMsg` (`8129`) — **после** `await`:

```js
const clan = await ClanModel.findOne({ 'members.telegramId': authed.telegramId });
if (!clan) return ...;
_lastChatAt = now;      // ← 300 сообщений в одном тике уже прошли проверку
```

Для `clanChat` это 300 индексированных запросов и 300 сообщений всем онлайн
членам клана за раз (флуд в клановый чат мимо лимита в 3 с). Для `privMsg` —
см. H3, там цена запроса на порядок выше.

**Что делать.** Присваивать `_lastChatAt = now` до первого `await`, откатывая
при отказе — ровно тот приём, который уже применён в `marketList`
(`_prevListAt`, `index.js:6631`).

### M7. `clanChatHistory` не чистится

```js
// server/index.js:2764
const clanChatHistory = new Map(); // clanId -> [до 30 сообщений]
```

Записи добавляются в `_recordClanChat` и не удаляются никогда — ни при

### M8. `completeSpecialQuest` — read-modify-write по xp/gold

```js
// server/index.js:9156
if (quest.reward.gold)  upd['savedData.gold'] = (authed.savedData.gold || 0) + quest.reward.gold;
if (quest.reward.xp)    upd['savedData.xp']   = (authed.savedData.xp   || 0) + quest.reward.xp;
```

`authed.savedData` — снимок, загруженный при логине, и он **не** обновляется

Once-only гарантия (`$ne` в фильтре) работает правильно — проблема только в
самих начислениях. `nexum` тут же сделан правильно, через `_incBalance`.

**Что делать.** `$inc` для `savedData.gold`/`savedData.xp` вместо вычисленного
абсолюта, как это уже сделано для балансов и `seasonPoints`.

## Низкий приоритет

**L1. `getRating(tab: 'clans')`** (`index.js:6870`) читает **все** кланы и всех
их участников на каждый запрос, 40 раз за 5 секунд на сокет. N+1 убрали, но
полный проход по коллекции остался.

**L2. `_broadcastMapBlips`** (`Room.js:1919`) на каждый уникальный ключ
`(arm, lane)` делает **два** прохода по всем 7129 мобам (сначала посчитать,
потом заполнить). Раз в секунду и только при открытой карте, но при нескольких
зрителях в разных зонах это до десятка полных проходов в секунду.

**L3. Финальный маркер дельт** (`Room.js:1584`) — `this.enemies.forEach` по всем
7129 мобам на каждом касте (20/с = 142 000 итераций/с), в том числе по мобам,
которых в этом касте никому не отправляли.

**L4. `_race10TrackHit`** (`index.js:7332`) на **каждый** удар по боссу Башни
делает `[..._race10.dmg.values()].sort(...)` — аллокация массива и сортировка
на горячем пути. При 30 бегунах это 30 элементов × сотни ударов в секунду.

**L5. `NaN` в CC-таймерах.** `Math.min(undefined, 6)` = `NaN` в
`applySkillEffect` и `pvpSkillCC` при пакете без `duration`. Сейчас безвредно
(`NaN > 0` — false), но `stunTimer` становится `NaN` навсегда и «отравляет»
любой будущий `Math.max`.

**L6. `_verifyAdminToken`** (`index.js:1168`) — срок жизни токена 7 дней,
инвалидации нет: смена `ADMIN_PASSWORD` отзывает старые токены (HMAC на нём),
но утёкший токен живёт неделю, и `/health` с ним отдаёт метрики процесса.

## Что сделано хорошо

Отмечаю отдельно, потому что при таком списке легко решить, что всё плохо — это
не так. Экономическая часть закрыта на уровне, который редко встречается:

* **Все деньги — через `$inc`.** `_incBalance`/`_spendBalance` с `$gte`-фильтром
  делают «проверить и списать» одной атомарной операцией. Ни одна гонка на
  балансах невозможна.
* **Ценз предметов** (`_itemCensus`/`_censusOverflow`) — инвариант «клиентский
  сейв может только уменьшать набор предметов» ловит любую генерацию вещей одним
  правилом вместо проверки на каждую фичу.
* **Леджер опыта** (`_allowXp`/`_xpCeilingFor`) считает, а не угадывает: сервер
  сам выдаёт каждое очко XP, поэтому сравнение точное, а множители забанкованы
  по максимуму — честный игрок не может пострадать.
* **Крафт, заточка, боксы, лут** переехали на сервер целиком.
* **Изоляция инстансов** (`_raceVisible`/`_playerLaneKey`) выдержана
  последовательно во всех путях: AI, стриминг, визуалы, пати-шаринг, профили.
* **`_idx` как сетевой хендл** с free-list — редкий случай, когда переиспользование
  идентификаторов сделано корректно и задокументировано.
* **Клиентский цикл** — адаптивный `_renderEveryN`, `try/finally` вокруг кадра
  (кадр не убивает всю сессию), раздельные `dt`/`realDt`, ограниченные пулы
  частиц и цифр урона.

## Порядок работ

Сгруппировано по «цена исправления против цены бездействия».

**Сегодня — эксплойты, стоящие реальных денег (C1, C2, C3, H6).**
Все четыре — один и тот же пропуск: событие, которое ничего не проверяет,
лежит в «быстрой» корзине лимитера. Общая часть решения — серверный кулдаун и
перенос в `_HEAVY_EVENTS`; дальше каждое по своей специфике (расход зелья,
проверка приглашения, кламп длительности). Пока они открыты, любой приз в GRAM
и Liberty выдаётся не тому, кто выиграл.

**На этой неделе — доступность (H3, H5) и память клиента (H4).**
H3 и H5 — это два индекса и три строки перестановки, а закрывают они самый
дешёвый способ положить базу. H4 — это переиспользовать уже написанный
`pixiInvalidateChunks` в виде LRU; именно он, по всем признакам, стоит за
жалобами «чем дольше играю, тем хуже».

**Дальше — гриферство и нагрузка (H1, H2, M3, M4).**

что определит, где именно упрётся потолок онлайна после снятия ограничений
из `AUDIT-PERF.md`.

**Потом — корректность (M5, M6, M7, M8) и защита в глубину (M1, M2).**

**Отдельно — регресс-проверки.** В `dev/` уже есть стенд
(`storage-race-check.js`, `xp-ledger-check.js`, `fanout-check.js`) — стоит
добавить туда сценарии на C1 (лечение без зелий), C3 (вступление в чужую пати) и
