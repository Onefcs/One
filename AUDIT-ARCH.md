## 1. Что уже сделано правильно

Это важно зафиксировать, потому что дальнейшие рекомендации — продолжение
существующей линии, а не её пересмотр.

**Вынесение уже идёт и даёт результат.** За последнюю неделю `server/index.js`
сократился с 14 050 строк до 10 370 (−26 %) шестью коммитами:

```
30ffdc1  Split loot/shop/market config out of server/index.js
b8d76af  Split player log and admin REST API out of server/index.js
abfa159  Split Telegram bot and client-bundle build out of server/index.js
d88e935  Split Death Battle, 3v3 Arena and Guild War out of server/index.js
436fc04  Split Кровавая Башня (race10) out of server/index.js
fabbc93  Split Страх (Fear) out of server/index.js
4ff12b1  Split Coop and Elite Farm Zone 2 out of server/index.js
```

Приём везде один: `module.exports = function createX(deps)` — фабрика, которой
явно передают нужные ей куски окружения. Каждый такой коммит проверен eslint и
`dev/harness.js`. Модули вынесены **дословно**, без попутного переписывания, —
это правильный способ, при нём диффы читаемы, а регрессии ловятся тестом.

**Клиент уже разбит, и разбит осознанно.** `server/bundle-files.js` держит список
из 24 файлов в порядке конкатенации, а `eslint.config.js` парсит их espree и
собирает общую область видимости, чтобы `no-undef` работал по-настоящему на
скрипте, который в браузере — один общий scope. Комментарий там объясняет, почему
регулярка не годится (`let player = null, dungeon = null;`). Это заметно выше
среднего уровня внимательности.

**Есть страховочная сетка.** CI (`.github/workflows/ci.yml`) гоняет `npm run lint`
и `node dev/harness.js` — настоящий сервер против in-memory Mongo с реальными
socket.io-клиентами. Плюс отдельные проверки в `dev/`: `item-loss-check`,
`xp-ledger-check`, `storage-race-check`, `snapshot-check`, `fanout-check`. Именно
это делает дальнейшее разбиение безопасным: рефакторинг без такого теста был бы
авантюрой, а с ним — рутиной.

**Общий код действительно общий.** `shared/definitions.js` (2 120 строк) и
`shared/netcodec.js` подключаются и сервером через `require`, и клиентом через
бандл. Формулы, стоимости и таблицы не продублированы между клиентом и сервером —
для игры с серверным авторитетом это главное, что можно было сделать правильно.

## 2. Где предел текущего подхода

Вот суть аудита.

`server/index.js` — 10 370 строк. Из них **7 995 строк (77 %) — это тело одного
колбэка** `io.on('connection', socket => { ... })` со строки 2290 по 10285. Внутри
него — **133 обработчика** `safeOn(...)`.

Все вынесения, перечисленные выше, вынимали из файла **модульное состояние** —
`_a3` для арены, `_db` для битвы на смерть, очереди, таймеры, расписания. А сами
обработчики остались на месте. Проверить это можно на `arena3Register`: модуль
`server/game/arena3.js` существует, но обработчик по-прежнему живёт в закрытии
`connection` в `index.js` и лезет одновременно в `_a3`, `_db`, `authed` и
`currentRoom`.

Поэтому файл и не падает ниже ~10 000 строк, сколько бы режимов ни вынесли:
режимы кончились, а 133 обработчика — нет.

**Почему тем же приёмом их не вынести.** Обработчики сидят в закрытии
per-socket-состояния, и держатся за него плотно:

| Переменная закрытия | Обращений внутри `connection` |
|---|---:|
| `authed` | 539 |
| `_lastStats` | 515 |
| `safeOn` | 136 |
| `currentRoom` | 149 |
| `socket.data` | 57 |
| `currentFloor` | 46 |

Фабрика `createX(deps)` вынимает **синглтон уровня модуля** — один `_a3` на
процесс. Обработчик `equipItem` — это **состояние одного соединения**, своё у
каждого игрока. Разные вещи, и одним приёмом не берутся.

Что при попытке всё же взять тем же приёмом — уже видно по числу зависимостей у
последних вынесенных модулей:

```
death-battle  ~11 deps      arena3  ~15 deps      race10  ~14 deps
coop          ~43 deps      farm2   ~42 deps      fear    ~45 deps
```

Первые три — самостоятельные автоматы с узким стыком. Последние три уже тянут за
собой по сорок с лишним имён: список зависимостей начинает повторять всё
окружение, и объект `deps` превращается в неявный God Object, просто написанный
руками. Ещё пара таких вынесений — и связность формально «уменьшится», а понимать
код станет тяжелее, чем было.

**Вывод: следующий шаг требует другого приёма — не фабрики модуля, а объекта
сессии.**

## 3. Что делать с `server/index.js`

### Приём: объект сессии вместо закрытия

Один раз ввести per-connection объект и передавать его в модули обработчиков:

```js
// server/session.js
function createSession(socket, deps) {
  return {
    socket, authed: null, lastStats: null,
    currentRoom: null, currentFloor: FLOOR_IDS.hub,
    // сюда же переезжают _persistSavedFields, _grantGold, _goldNow,
    // _serverSpendGold — всё, что сейчас живёт в закрытии и требует authed
  };
}

// server/handlers/market.js
module.exports = function registerMarket(session, safeOn, deps) {
  safeOn('marketBrowse', async () => { /* тело переезжает дословно */ });
  safeOn('marketList',   async () => { ... });
  // ...
};

// server/index.js — то, что от него остаётся
io.on('connection', socket => {
  const s = createSession(socket, deps);
  registerAuth(s, safeOn, deps);
  registerMarket(s, safeOn, deps);
  registerClan(s, safeOn, deps);
  // ...
});
```

Механическая часть: `authed` → `s.authed`, `_lastStats` → `s.lastStats`. Это
sed-замена по вынимаемому куску, а не переписывание логики. Тела обработчиков
переезжают дословно — ровно как в предыдущих шести коммитах.

**Начать с рынка (479 строк, 6 обработчиков).** Он самый изолированный: у него уже
есть свой `server/market-helpers.js`, он не трогает бой и почти не трогает
`currentRoom`, а `dev/harness.js` покрывает рыночные сценарии. Это дешёвая
проверка самого приёма на маленьком объёме — если объект сессии где-то неудобен,
выяснится на 479 строках, а не на 990.

**Кланы вторыми** — крупный связный кусок, уже есть `js/clans.js` на клиенте и
`models/Clan.js`, границы домена очевидны.

**Auth/сессия — последним и осторожно.** Там `selectChar` (634 строки — самый
большой обработчик в файле), `saveProgress` и `disconnect`: именно они создают и
разрушают то самое состояние, ради которого вводится объект сессии. Пока остальное
не переехало, трогать их незачем; когда переедет — станет понятно, каким этот
объект должен быть на самом деле.

### Ожидаемый итог

`index.js` уходит примерно с 10 370 к 2 000–2 500 строкам: старт Express/Mongo/
Socket.io, конфигурация, `_buildGameStartPayload`, кросс-режимный клей
(`_pvpFrozen`, `_pvpEliminate`, `_reclaimQueues`), и сама сборка сессии. То есть
файл наконец становится тем, чем называется, — точкой входа.

### Ещё 2 289 строк выше закрытия

Модульная часть `index.js` (строки 1–2290) тоже содержит готовые к вынесению
связные группы, и они берутся **текущим приёмом**, без объекта сессии:

- баланс/валюты — `_balanceCache`, `_incBalance`, `_spendBalance` → `server/balance.js`
- история чата и ЛС — `_recordChat`, `_recordClanChat`, `_recordDm`, `_loadChatHistory`, `_trimChatHistory`, `_publicChatHistory` → `server/chat-store.js`
- рейтинги — `_cachedRating`, `_ratingPlayers`, `_ratingClans`, `_refreshTopPlayer` → `server/ratings.js`
- дневные лимиты — `_lockDailyAttempt`, `_dailyAttemptsLeft`, `_lockDailyMinutes`, `_dailyMinutesLeft` и десяток одинаковых обёрток над ними (`_lockArena3Daily`, `_lockRace10Daily`, `_lockFearDaily`, `_lockCoopDaily`, `_lockFarm2Minutes`…) → `server/daily-limits.js`

Последний пункт — самый простой и самый выгодный: там сейчас 12 однострочных
обёрток, отличающихся только именем поля. Их можно вынести хоть сегодня, отдельным
коммитом, не дожидаясь решения по объекту сессии.

## 4. Что делать с `js/ui.js`

7 481 строка, **422 верхнеуровневых имени** в общей области видимости бандла.
Внутри — теплопорталы, портрет в инвентаре, продвинутые навыки, справочник
фарм-зоны, лутбоксы, вкладки Кровавой Башни / Страха / Coop / элитной фарм-зоны /
Войны гильдий, покупка, продажа, обработчики серверных событий, переключатель
звука, выбор языка, модалки депозита и вывода. Это не «UI-модуль», это весь
интерфейс игры одним файлом.

Разбивается он **дешевле, чем сервер**: бандл — общий scope, порядок задаётся
`server/bundle-files.js`, поэтому вынесение куска в новый файл не требует ни
импортов, ни экспортов. Достаточно вырезать строки, положить в новый файл и
дописать его в список. eslint проверит, что ни одно имя не потерялось, — ради
этого `bundleGlobals()` в конфиге и написан.

Резать по вкладкам, они уже размечены комментариями-заголовками:

| Новый файл | Что забирает | Примерно строк |
|---|---|---:|
| `js/ui-events.js` | вкладки режимов: Кровавая Башня, Страх, Coop, элитная фарм-зона, Война гильдий (4639–5977) | ~1 300 |
| `js/ui-market.js` | покупка/продажа (5977–6223) | ~250 |
| `js/ui-gram.js` | модалки депозита и вывода (7212–конец) | ~270 |
| `js/ui-codex.js` | справочник фарм-зоны, лутбоксы (1764–2133, 3585+) | ~600 |
| `js/ui-skills.js` | навыки, пассивки, продвинутые навыки (776–1001) | ~230 |
| `js/ui-profile.js` | звук, язык (6857–7212) | ~350 |

Остаётся ~4 400 строк базового UI — уже обозримо. Пять из шести кусков ни от чего,
кроме `state`/`i18n`/`definitions`, не зависят, так что порядок в бандле не
ломается.

### Отдельно: цикл `ui.js` ↔ `network.js`

Граф глобальных имён показывает взаимную зависимость:

```
js/ui.js      использует  71 имя из js/network.js
js/network.js использует  93 имени из js/ui.js
```

В общем scope это работает и падать не будет — но означает, что на ES-модули эти
два файла в текущем виде не переводятся: получится цикл. Если когда-нибудь
захочется настоящих модулей, начинать придётся с разрыва этой пары, а не с
подключения сборщика.

Практический шаг сейчас — не разрывать, а **не углублять**: в `network.js` из
`ui.js` зовутся в основном рендер-функции по серверным событиям. Секция
`// ── Server event handlers (called from network.js)` в `ui.js` (строка 6223) —
это и есть стык. Собрав его в один явный объект (`UI.onServerEvent.*`), вы
сведёте 93 имени к одному, и связка станет описуемой, даже если файлы останутся
как есть.

## 5. Находки попутно: две причины красного CI

Не архитектура, но нашлось при проверке и чинится в одну строку — **уже
исправлено в этом коммите**.

```
server/index.js
  171:36  error  'REBIRTH_COST' is assigned a value but never used  no-unused-vars
✖ 1 problem
```

Коммит `ee4829e` («Revert rebirth cost to "every 5th doubles" and harden it»)
перевёл обработчик `rebirth` на `rebirthCostFor(...)`, но `REBIRTH_COST` остался в
списке импортов из `shared/definitions.js`. Само по себе безвредно — но
`npm run lint` падает, а значит **CI на ветке красный и любой PR с неё не
пройдёт**. Убран мёртвый импорт; `npx eslint .` теперь чистый.

Показательно, что это ровно тот класс ошибки, ради которого конфиг eslint и
писался, — комментарий в его шапке описывает именно «неимпортированная константа,
мёртвая ветка условия».

### 5.2. Гонка в самом тесте: `race10State` (тоже исправлено)

`node dev/harness.js` на этой машине дал **575 passed, 2 failed** — обе в сценарии
«race10: 51 entrants for 50 corridors»:

```
FAIL the refused entrant is unregistered ... — got undefined, want false
FAIL and is not in the match either        — got undefined, want false
```

Это **не баг продукта, а гонка в тесте**, и она объясняется ровно тем, о чём весь
этот аудит. Событие `race10State` шлётся из двух мест с разной формой полезной
нагрузки:

- `_race10Broadcast()` в `server/game/race10.js` — широковещательно, только
  публичное состояние, **без** `registered`/`inMatch`;
- обработчик `race10Sync` в `server/index.js:8195` — лично в ответ на запрос,
  **с** `registered`/`inMatch`.

Клиент это различает намеренно и корректно: `js/network.js` сохраняет прежнее
значение, когда поля нет (`if (st.registered !== undefined)`). А тест брал
**первое пришедшее** `race10State` — и на загруженной машине широковещательный
пакет от развёртывания 50 участников успевал прийти раньше личного ответа. Отсюда
`undefined`.

Характерно, что в файле уже есть решение этой же задачи для `gameState` —
`waitForEnemyResync()` с комментарием «used to pick the actual enemyResync
response out of the room's own ordinary periodic broadcasts, which fire on the
same event name». Тот же приём здесь просто не был применён.

Исправлено тем же способом: у `waitFor()` появился необязательный предикат
`match`, а сценарий ждёт ответ по его собственной форме:

```js
const sync = rejected.wait('race10State', {
  timeout: 5000, match: st => st.registered !== undefined,
});
```

Почему это важно за пределами одного теста: **CI при этом падал бы через раз** —
на быстром раннере личный ответ обычно успевает первым, на медленном нет. Плавающий
красный тест обесценивает ту самую страховочную сетку, на которую опирается весь
план разбиения из разделов 3–4. Чинить это надо **до** начала вынесения, иначе
первый же плавающий прогон спишут на рефакторинг.

Отдельно стоит отметить и саму первопричину: один и тот же `race10State` с двумя
формами — прямое следствие того, что автомат режима уехал в `server/game/race10.js`,
а обработчик остался в `index.js`. Протокол в продукте корректен, но его половины
теперь живут в разных файлах и договорённость между ними нигде не записана. При
вынесении обработчиков (раздел 3) такие пары стоит сводить в один модуль.

## 6. Чего делать НЕ надо

Стоит сказать прямо, потому что при слове «архитектура» это предлагают по умолчанию.

**Не переводить клиент на ES-модули и сборщик.** Схема «конкатенация 24 файлов по
списку + eslint, знающий общий scope» работает, покрыта линтером и стоит ноль
секунд сборки. Переход на модули потребует сначала разорвать цикл `ui`↔`network`
(164 имени в обе стороны), затем расставить импорты по ~1 700 верхнеуровневым
именам — и не даст ничего, чего нет сейчас. Разбиение `ui.js` из раздела 4
работает **внутри** текущей схемы.

**Не трогать `server/game/Room.js` (3 521).** Это игровой цикл: тик, интерес,
рассылка. Он большой по существу задачи, а не по недосмотру, и `AUDIT-PERF.md`
показывает, что он на горячем пути. Резать его — риск без выгоды.
