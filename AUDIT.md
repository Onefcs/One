## Критично

### C1. Stored XSS через имя игрока

Имя аккаунта берётся из Telegram и нигде не фильтруется:

```js
// server/index.js:3333 (loginTelegramWebApp)
const username = user.username || user.first_name || `tg_${telegramId}`;
```

`user.username` (@handle) безопасен по формату, но **`first_name` — произвольная строка**, которую игрок меняет сам, и она попадает в аккаунт, если @handle не задан. Дальше эта строка вставляется в DOM без экранирования:

```js
// js/ui.js:2876 — таблица рейтинга
<div class="rating-name">@${r.username}...
// js/ui.js:3733 / 3970 — продавец на маркете
const sub = mode === 'buy' ? `@${l.sellerUsername || '?'}` : ...
// js/ui.js:4616 — список рефералов
<div class="ref-friend-name">@${f.username || ...}</div>
// js/ui.js:248 — чужой профиль
<div style="...">${fromName || profile.name}</div>
```

Все четыре — присваивание в `innerHTML`. CSP разрешает `'unsafe-inline'` (это записано осознанно, ради инлайновых обработчиков в `index.html`), поэтому payload исполняется. Достаточно попасть в топ-50 рейтинга или выставить лот на маркет — код выполнится у каждого, кто откроет панель.

Что можно сделать из такого payload: отправить любые socket-события от имени жертвы (перевести её вещи на маркет по 0.1 GRAM, вывести GRAM на свой кошелёк через `gramWithdrawRequest`), прочитать `localStorage` (там лежит бэкап сейва), в Telegram-вебвью — дотянуться до `Telegram.WebApp.initData`.

Показательно, что чат и клановые панели **экранированы правильно** (`_escHtml` в `js/network.js:1817`, `_esc` в `js/clans.js:893`) — то есть механизм в проекте есть, просто эти пять мест его не используют. Админка (`admin.html`) экранирует везде.

Починка: `_escHtml()` во всех пяти местах + серверная нормализация имени при логине (например `String(name).replace(/[<>&"]/g,'').slice(0,32)`), чтобы уже сохранённые имена перестали быть опасными.

### C2. Бессмертие: HP превращается в NaN

```js
// server/index.js:4369
safeOn('usePotion', ({ amount } = {}) => {
  if (currentRoom) currentRoom.healPlayer(socket.id, Math.min(amount || 60, 200));
});
```

`amount: "x"` → `"x" || 60` = `"x"` → `Math.min("x", 200)` = `NaN` → `Room.healPlayer`: `p.hp = Math.min(p.maxHp, p.hp + NaN)` = `NaN`.

Дальше NaN не лечится ничем:
* урон монстра — `closest.hp = Math.max(0, NaN - dmg)` = `NaN`;
* PvP — `target.hp = Math.max(0, NaN - dmg)` = `NaN`;
* проверка смерти `p.hp <= 0` при NaN всегда `false`;
* `syncPlayerHp` тоже не восстанавливает: `requested <= p.hp` → `false`, дальше снова `NaN`.

Игрок становится неубиваемым до следующего респауна/перезахода. Это ломает всё, где есть реальная награда: Битва на смерть (GRAM + предметы победителю), Арена 3х3 и Кровавая Башня (Liberty).

Тот же баг во второй руке: `healParty` (`server/index.js:4928`) — `Math.max(0, Math.min(Math.floor(amount), 9999))` при `amount: undefined` даёт NaN, то есть можно «залечить» до бессмертия члена группы. Причём соседний обработчик подземелья написан правильно: `Math.min(Math.floor(amount) || 0, 9999)` (`server/index.js:5644`) — то есть это именно недосмотр в двух местах, а не осознанное решение.

Побочный эффект: в бинарном пакете `hp` пишется как i32, `setInt32(NaN)` = 0, так что остальные видят «труп», который их убивает.

Починка: везде прогонять входное число через один helper — `const n = Number(amount); if (!Number.isFinite(n)) return;`.

### C3. Гонка «проверка → await → списание»

Три обработчика проверяют условие, потом делают `await`, и только потом списывают. Два события, отправленных подряд в одном тике, оба проходят проверку (лимитер разрешает 40 «тяжёлых» событий за 5 с):

**Магазин** (`server/index.js:3533`):
```js
if (_liveGram() < pkg.gram) return ...;          // обе копии проходят
const doc = await PlayerModel.findById(authed._id);   // окно
...
_setGram(_round7(_liveGram() - pkg.gram));       // списание дважды
```
Итог: два пакета за цену одного, баланс уходит в минус. Пакет `pkg100` — это 220 GRAM реальных денег.

**VIP-награды** (`server/index.js:4217`): `vipPending` читается из БД, потом `await`, потом очищается. Два вызова подряд выдают комплект наград дважды.

**Спецквесты** (`server/index.js:5654`): `done.includes(questId)` проверяется по `authed.savedData`, обновляется после `await` — награда начисляется дважды.

Починка: либо условное обновление в самой Mongo (`updateOne({_id, 'savedData.gramBalance': {$gte: price}}, {$inc: {...: -price}})` + проверка `modifiedCount`, что я подтвердил на живой БД скриптом `scripts/verify-balances.js`), либо per-socket мьютекс на «денежные» обработчики. Обратите внимание, что `marketBuy` уже сделан правильно — там между re-check и списанием намеренно нет `await`, и это прямо описано в комментарии; здесь та же дисциплина просто не применена.

## Высоко

### H1. Скиллы без серверного кулдауна

`attackEnemy` защищён: не чаще одного удара в 150 мс, проверка дистанции и линии видимости (`Room.js:1626-1639`). А `skillAttackEnemy` (`Room.js:1672`) — **без кулдауна вообще**, только клемп множителя `[1,10]`. Ограничивает его лишь `_atkAllowed()` — 20 событий/с.

Хуже с PvP: `pvpSkillAttack` (`server/index.js:4727`) не вызывает `_atkAllowed()` вовсе, то есть попадает в «быстрое» ведро — 1500 событий за 5 с (300/с). Кулдауны скиллов живут только в клиенте. Модифицированный клиент делает ~300 ударов в секунду с множителем 10 — мгновенное убийство любого игрока и любого босса.

Починка: перенести проверку кулдауна на сервер (per-skill timestamp в `p._skillCd`) или как минимум добавить `_lastSkillAtk` с тем же 150-мс шагом и провести `pvpSkillAttack` через `_atkAllowed()`.

### H2. `spawnProj` / `spawnAoe` — неограниченная ретрансляция

```js
safeOn('spawnProj', data => { socket.to(`floor_${currentFloor}`).emit('spawnProj', data); });
safeOn('spawnAoe',  data => { socket.to(`floor_${currentFloor}`).emit('spawnAoe',  data); });
```

`data` не валидируется ничем. Лимит сообщения — 512 КБ (`maxHttpBufferSize`), ведро «быстрых» событий — 300/с. Один клиент может рассылать по 512 КБ каждому игроку на этаже: при 200 онлайн это ~100 МБ на одно событие. Плюс произвольный объект попадает в чужие обработчики отрисовки.

Починка: собирать пакет на сервере из белого списка полей (x, y, angle, тип, id скилла) с числовой валидацией; не пересылать клиентский объект как есть.

### H3. Зависимости

`npm audit` (проверено на текущем lock-файле):
* **socket.io-parser** 4.0.0–4.2.6 — `GHSA-2m8v-j782-fhvr`, memory exhaustion. Это основной сетевой вход игры, эксплуатируется удалённо без авторизации. Чинится `npm audit fix`.
* **tar ≤7.5.20** — critical (12 advisories), тянется через `@mapbox/node-pre-gyp` → **bcrypt**. При этом `bcrypt` не используется в проекте нигде: `grep -rn bcrypt server/ js/` пусто, админ-логин сравнивает пароль через `crypto.timingSafeEqual`. Зависимость можно просто удалить и закрыть critical без breaking change.
* brace-expansion — high, транзитивно, dev-путь.

### H4. HTML-инъекция в сообщения администратору

Все уведомления боту уходят с `parse_mode: 'HTML'` и подставляют пользовательские строки без экранирования:

```js
// server/index.js:370-376 (notifyAdminGram)
`👤 ${tx.username} (<code>${tx.telegramId}</code>)`,
`💎 ${tx.amount} GRAM`,
isDeposit ? `🏷 Мемо: <code>${tx.memo}</code>` : `📬 Адрес: <code>${tx.address}</code>`,
```

`memo` и `address` приходят прямо из клиента (`gramDepositRequest`/`gramWithdrawRequest`), `username` — из Telegram `first_name`. Игрок может закрыть `</code>` и дорисовать в сообщении администратора любой текст — например другую сумму или «уже подтверждено», прямо над кнопками ✅/❌. Это социальная инженерия против того, кто руками подтверждает выплаты.

То же в `_notifyAdminNewPlayer` (`:550`) и в приветствии бота (`:596`, там `firstName` — самому себе, но сломанный HTML заставит Telegram вернуть 400 и сообщение не придёт вовсе).

Починка: экранировать `& < >` во всех подстановках либо перейти на `parse_mode` без разметки для полей, пришедших от пользователя.

### H5. Позиция игрока не проверяется

```js
// Room.js:1290
updatePlayerPos(socketId, x, y, facing) {
  ...
  p.x = x; p.y = y; p.facing = facing;
}
```

Нет ни проверки на число, ни на скорость, ни на стены. Следствия: телепорт в любую точку мира (в том числе внутрь геометрии и мимо запертых «рук» с уровневым требованием), мгновенный обход всех дистанционных проверок боя, а `x: NaN` выбивает игрока из пространственной сетки AOI (`Math.floor(NaN)`), делая его невидимым для чужих клиентов.

Починка: `Number.isFinite` на входе + клемп максимального смещения за тик по `CHAR_DEF.speed` с запасом (то же для `raidMove`/`partyDungeonMove`).

## Средне

**M1 (исправлено).** Балансы через `$set`. Все пути начисления GRAM/Liberty, кроме `_grantPartyDungeonNexum`, читают значение, прибавляют и пишут целиком. Две операции в одном окне затирают друг друга — это то, что уже зафиксировал предыдущий аудит; мой прогон `scripts/verify-balances.js` на MongoDB 8.2.6 подтвердил, что `$inc` по точечному пути + условие `$gte` решают задачу (7/7 проверок), и что без условия в фильтре сам по себе `$inc` от гонки не спасает (баланс уходит в −60).

**M2. Админ-выдача.** `/admin/player/:tid/give` (`:983`): `gram` и `nexum` защищены живым кэшем, а `gold` — нет. У онлайн-игрока ближайший автосейв (до 60 с) перезапишет `savedData.gold` клиентским значением, и выданное золото исчезнет. Плюс `Number(gold)` не проверяется: `"abc"` → `NaN` попадает в БД и ломает клиент.

**M3. Вкладка транзакций в админке пуста.** Сервер отдаёт `res.json({ txs })` (`:1111`), панель читает `d.transactions` (`admin.html:817`) — список всегда пустой. Единственный оставшийся путь модерации заявок — кнопки в Telegram.

**M4. Строки >255 байт в бинарном протоколе.** `_ncWStr` (`shared/netcodec.js:79`) пишет длину одним байтом: `_ncU8[o] = b.length` — при 256+ байтах длина заворачивается, а данные пишутся полностью, и декодер разъезжается по всему пакету. Telegram `first_name` — до 64 символов; эмодзи по 4 байта дают 256. Один игрок с таким именем ломает `gameState` всем, кто его видит.

**M5. `getRating(tab:'clans')`** (`:4192`) делает отдельный `aggregate` на каждый клан в цикле. 100 кланов — 100 агрегаций на один запрос, до 40 запросов за 5 с с сокета. Заменяется одним `$group` по всем участникам.

**M6. `skillEffect`** (`:4654`) принимает `enemyIds` любой длины и прогоняет цикл в потоке игрового цикла. 512 КБ ids × 300 событий/с — прямой стол для DoS тика.

**M7. Дневные попытки.** `_lockDailyAttempt` (`:1797`) читает счётчик, прибавляет 1 и пишет `$set` — параллельные старты теряют инкремент. Нужен `$inc` с фильтром по дате.

**M8. Кланы.** `clanApprove`/`clanKick`/`clanLeave`/`clanApply` читают документ и сохраняют целиком (`clan.save()`). Два действия лидера подряд (или заявка одновременно с одобрением) теряют одно из изменений. XP клана уже переведён на `$inc` — здесь та же логика напрашивается ($push/$pull).

**M9. Callback бота.** `_handleAdminCallback` (`:412`) обрабатывает `gram_ok:<id>` из любого `callback_query`, не проверяя `cq.from.id === TG_ADMIN_ID`. Сейчас кнопки существуют только в чате администратора, так что практически недостижимо, но проверка отправителя здесь стоит одну строку.

**M10. Fail-open проверки подписи.** `verifyTelegramAuth`/`verifyTelegramWebApp` (`:635`, `:652`) при пустом `TG_BOT_TOKEN` считают HMAC с пустым ключом — то есть подпись сможет подделать кто угодно и войти под любым `telegramId`. Пока переменная задана, это не эксплуатируется, но одна ошибка деплоя превращается в полный обход авторизации. `if (!_TG_TOKEN) return null;` закрывает.

**M11. Рост памяти.** `dmHistory` (`:1662`) хранит по 50 сообщений на каждую пару собеседников и никогда не чистится; `_loginFails` (`:847`) — запись на каждый IP навсегда. За месяц аптайма это заметно.

## Низкий приоритет

* **L1.** `/health` (`:1269`) отдаёт без авторизации heap/rss, число сокетов, тайминги тика. Полезно для мониторинга, но и для того, кто ищет момент нагрузки.
* **L2.** `applyLocale` (`js/i18n.js:1307`): исключение TDZ на `_activeQuestTab` ловится, но обрывает остаток блока — при старте не выполняются `renderVipPanel` и `_renderLangPicker`. Достаточно перенести проверку `_activeQuestTab` в конец или обращаться через `window._activeQuestTab`.
* **L3.** Админ-эндпоинты без rate-limit (кроме `/admin/login`); токен живёт 7 дней и не отзывается при смене пароля… точнее отзывается, так как подпись на пароле — но нет способа разлогинить одну сессию.
* **L4.** `POST/PUT /admin/special-quests` (`:1243`) передают `req.body` прямо в модель (mass assignment). Админ-доступ, но валидация полей не помешает.
* **L5.** `cors: { origin: '*' }` на socket.io (`:713`) — любой сайт может открыть сокет; без initData он ничего не сделает, но и анонимный коннект чего-то стоит.
* **L6.** Цикл AI обходит **все** ~4500 мобов 40 раз в секунду независимо от того, есть ли рядом игроки (`Room.js:546`). Это основной фиксированный расход CPU после недавних оптимизаций; следующий шаг — «активный набор» (агрессивные + те, у кого в радиусе есть игрок) и редкий проход по остальным ради респауна.
* **L7.** Буфер кодека `_ncBuf` только растёт и никогда не отдаётся обратно (`netcodec.js:52`).
* **L8.** `gramWithdrawRequest` (`:3482`) списывает баланс до создания `GramTx`; если создание упадёт, GRAM исчезнет без заявки (в лог попадёт, но возврата нет).

## Что сделано хорошо

Это не формальность — многие вещи, которые в таких проектах обычно и ломаются, здесь закрыты:

* **PvP полностью серверный**: урон применяется в `Room.pvpAttack`, клиент не сообщает «сколько я получил» — прямо отмечено в комментарии как исправление старой дыры.
* **`updatePlayerStats`** якорит принимаемые статы к независимо вычисленному `computeStats` (не к предыдущему значению от клиента), крит вообще берётся только серверный.
* **`_canonSavedItem` / `_canonicalMarketItem`** пересобирают каждый предмет из каталога — придумать статы нельзя.

### Инцидент с порогом перемещения (H5)

Первая версия проверки позиции была выкачена в прод и сломала игру: телепорт-пады
в хабе («1 уровень», «20 уровень», …) двигают игрока на десятки тысяч пикселей, и
делает это **клиент** — он ставит себе координату и сообщает её серверу. Порог
рубил этот прыжок, клиент откатывался обратно на пад, пад срабатывал снова — и
так по кругу: баннер «→ 1 уровень» много раз подряд и невозможность уйти из хаба.
Правки откачены (`f6470b8`), причина найдена, проверка переписана.

Проверка была переписана так, чтобы знать про штатные точки прибытия (список
собирался из тех же данных мира, из которых клиент строит пады), и в таком виде
прошла все проверки — включая живого клиента в браузере. **После этого
ограничение на дальность было снято совсем, по решению владельца проекта.**
Осталась только защита от нечисловых координат: `NaN` в позиции выбивает игрока
из пространственной сетки, делая его невидимым для других и недосягаемым для
AI, — это не правило перемещения, а защита состояния комнаты.

Что это значит на практике: перемещение снова полностью на стороне клиента.
Модифицированный клиент может телепортироваться куда угодно — например к
дальнему боссу или в руку, до которой не дорос по уровню. Взамен исключён целый
класс поломок, где правило перемещения ошибочно срабатывает на живых игроках.
Если возвращать — возвращать вместе со списком законных точек и обязательно с
прогоном по всем падам.

**Осталось сознательно нетронутым:**

* **L5 (CORS `origin:'*'`)** — сузить источник до домена игры можно, но Telegram
  открывает Mini App из нескольких origin (web.telegram.org, нативные вебвью), и
  без прогона на всех клиентах это риск выкинуть часть игроков ради выгоды,
  которой почти нет: без initData сокет всё равно ничего не может.
* **L6 (активный набор мобов)** — чистая оптимизация цикла AI на ~4500 мобов.
  Это переписывание горячего пути, которому нужен свой нагрузочный прогон;
  в набор правок по безопасности оно не помещается.
* **L7 (буфер кодека только растёт)** — безвредно, трогать смысла нет.
